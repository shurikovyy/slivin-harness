# Проверка композиции исправлений отчётов

База: `51762e751de010487f9845c3d6647a1fe92016f7`.

## Подтверждённые дефекты и изменение поведения

1. При полностью описанном материальном замечании и ошибочном общем PASS
   исправление одного статуса требовало дописать новое замечание. Теперь новое
   замечание не требуется: сохраняются исходные findings и ссылки, а существующий
   Controller продолжает проверять единственно допустимый неположительный статус.
2. При отсутствующей ссылке на уже существующее замечание механизм требовал
   дублировать замечание. Теперь разрешено привязать существующий finding_id;
   исходные findings неизменны, отсутствующий ID нельзя принять.
3. Взаимоисключающие LOCAL/CLOSURE режимы останавливали последовательность двух
   разрешённых исправлений. Теперь переходы могут следовать друг за другом в
   прежнем общем лимите двух дополнительных ответов, с не более чем одной closure.
   Каждая следующая операция проверяется относительно уже проверенного предыдущего
   отчёта. Исправление не разрешает откатывать предыдущее или менять остальные claims.
4. Разбиение MISSING_FIELDS на отдельные ошибки теряло исходный failure_kind.
   Теперь классификация сохраняется: ошибки целостности и технические конфликты
   не становятся локальной коррекцией из-за пакетирования.

5. При переходе PASS → REPLAN_REQUIRED прежний пустой top-level reason нельзя
   было заполнить, хотя новый статус обязан иметь причину. Теперь разрешено
   заполнить только эту пустую сводную причину; причины в строках, отрицательные
   claims и существующие findings остаются неизменными. Пустая причина не принимается.

## Что не меняется

Не меняются роли, схемы основных отчётов, критерии принятия, origin catalogue,
проверки исходного кода и результата, доказательства независимого Evaluator,
ограничения файловой системы, candidate/Git/runtime integrity, количество
квалификационных заданий и количество разрешённых ответов модели.
Отрицательный claim нельзя убрать/сделать положительным ради PASS. Существующий
finding нельзя переписать. Новый finding обязан быть использован разрешённой
ссылкой; произвольное добавление или дубликат отклоняются. Полная семантическая
валидация остаётся после коррекции. Материальные замечания продолжают требовать
исправления продукта или пересмотра плана, а не выдачи успеха.

## Упрощение

Убрана искусственная несовместимость двух механизмов коррекции. Новых ролей,
реестров, этапов qualification и дополнительных обращений к модели нет.
Отвергнуты: увеличить retry budget, принять противоречивый PASS, удалить исходное
замечание, ослабить ограничения вне исправляемых полей, считать наличие JSON
доказательством правильного кода.

## Проверка и её границы

В пакете 18 targeted regressions (фактическое число см. unittest log). Часть проверяет
настоящие функции closure; тесты маршрута извлекают и исполняют действующую nested
admit_phase из evaluator.py с контролируемыми ответами модели и упорядоченными
диагностическими ошибками. Это тест маршрутизации, не модельный и не продуктовый
benchmark. Существующие полные evaluator/integration tests остаются необходимыми.

См. TEST_RESULTS.json для фактически выполненных проверок в среде сборки.
Нативная Windows/Codex qualification и _90 этим пакетом не объявляются пройденными.
Успешное прохождение ограниченного набора тестов не доказывает отсутствия всех
дефектов или обязательного успеха любой задачи.

## Применение

Самодостаточный apply_recovery_fix.py проверяет точную Git-базу, отсутствие tracked
правок и совпадение заменяемых исходников. Сначала готовит все изменения и резервную
копию, затем применяет их. Выполняет targeted tests без модели; при отказе
восстанавливает затронутые файлы. Не делает commit/push, не меняет credentials,
.env, зависимости и внешние проекты. Запуск из корня slivin-harness:

    py.exe -3 C:/Users/Slivin.Aleksandr/Downloads/HARNESS_RECOVERY_AUDIT_51762e7_v2.py

После применения успешные targeted tests не являются разрешением считать
RELEASE_QUALIFIED полученным. Подробный patch сохраняется рядом с резервной копией.

Применитель v2 сверяет содержимое с Git HEAD после нормализации только CRLF → LF. Кодовые изменения не допускаются; исходные байты сохраняются для отката.
